# HeatRoute

Сервис автоматического построения вариантов подключения перспективных ОКС
к существующей тепловой сети.

Конкурсный кейс «Сервис моделирования трасс подключения к тепловым сетям»,
«Лидеры цифровой трансформации» 2026.

На вход — один GeoJSON с существующей сетью, камерами, перспективными ОКС, точками
подключения и пространственными ограничениями. На выходе — до трёх ранжированных
вариантов новой сети с маршрутами, точками врезки, камерами, расходами, условными
диаметрами, участками реконструкции существующей сети и полной стоимостью.

## Быстрый старт

```bash
cp .env.example .env
docker-compose up -d --build
```

| Что | Адрес |

| Swagger UI | http://localhost:8080/swagger-ui.html |

### Разработка

```bash
cd backend  && mvn spring-boot:run -Dspring-boot.run.profiles=nodb   # без базы данных
cd backend  && mvn test                                             # 67 тестов
cd frontend && npm run dev                                          # сервер разработки
cd frontend && npm run e2e                                          # сквозные тесты в браузере
```

Сквозные тесты идут против поднятого стека: сначала `docker-compose up -d`.

Развёртывание с нуля — так, как его увидит чужая машина: клон репозитория, сборка
образов без кеша, подъём одной командой и сквозная проверка API и интерфейса.

```bash
bash ops/clean_room_check.sh
```

## Что реализовано

**Обязательный функционал (раздел 2.11 ТЗ)** — весь.

- Обработка всех перспективных ОКС за один запуск.
- Автоматический выбор точек врезки с применением правила 10 м.
- Определение совместного или раздельного подключения по расстоянию в графе.
- Соблюдение пространственных ограничений таблицы 5.1, включая специальные проходы,
  минимальные углы пересечения и запрет самопересечений трасс: внутри одной части
  сети пересечение объединяется в общий узел, между независимыми частями — часть
  строится заново в обход уже принятых.
- Расчёт расходов, подбор условных диаметров, проверка предельной длины непрерывной
  части одного диаметра.
- Распространение дополнительного расхода к источнику, частичная реконструкция
  участка при врезке в его середину, реконструкция камер врезки.
- Стоимость и до трёх содержательно отличающихся вариантов с ранжированием по `S`;
  если разбиений ОКС на три варианта не хватило, различие даёт форма сети —
  эвристика запускается с другого затравочного терминала.
- Сохранение частичного результата и штраф за ОКС без маршрута.
- Выгрузка одним совмещённым GeoJSON по разделу 10 ТП.

**Дополнительная задача** — трассировка с учётом глубины: подбор глубины шагом 0,5 м,
прохождение пересечений сверху или снизу с выбором по стоимости, профиль с уклоном
не круче 0,10 м/м, коэффициент `Kгл`, Z-координаты в выгрузке. Если манёвр не помещается,
профиль возвращает замечание маршрутизации: место пересечения запрещается и вариант
строится заново.

**Сверх требований.** Протокол принятых допущений с кодами и списками объектов;
справочник технического приложения доступен через API; набор с полным атрибутивным
составом и тесты на нём; сквозные тесты интерфейса в браузере.

## Соответствие требованиям к стеку

Раздел 3.2 ТЗ выдержан без отклонений: Java 11, `spring-boot-starter-parent:2.6.3`,
PostgreSQL, `springdoc-openapi-ui:1.7.0`, docker-compose, Ubuntu Server 22.

Предел по объёму входа проверен загрузкой, а не настройкой: файл 3 ГБ на 1 262 935
объектов принимается и разбирается за 98 с при куче 5,7 ГБ — меньшей, чем даёт
требуемая ТЗ машина. Набор для такой проверки собирает `tools/make_large_dataset.py`.

Входной файл до 3 ГБ обрабатывается потоково через временное дисковое хранилище;
выгрузка до 500 МБ пишется в поток ответа курсором по строкам базы.

Координаты, идентификаторы и конфигурация конкурсного набора нигде не зафиксированы
в коде (раздел 2.14). Справочник технического приложения вынесен
в `backend/src/main/resources/reference/heatroute-reference.yml` и подменяется
снаружи без пересборки:

```bash
java -jar heatroute.jar --spring.config.additional-location=file:/opt/heatroute/
```

## Как устроен расчёт

```
GeoJSON → разбор и восстановление данных → поле препятствий → граф видимости
        → разбиение ОКС и точки врезки → дерево Штейнера → расходы и диаметры
        → реконструкция и стоимость → ранжирование → GeoJSON
```

Ключевое решение — **граф видимости вместо сетки**. Кратчайший путь в нём состоит
из прямых отрезков и огибает препятствия по касательной, то есть даёт ту геометрию,
которую рисует инженер. Сеточный поиск при любом шаге даёт ступенчатую линию,
а её сглаживание рискует нарушить только что соблюдённые клиренсы.

Подробности — в [`docs/02_ALGORITHM.md`](docs/02_ALGORITHM.md)
и [`docs/05_ДОКУМЕНТАЦИЯ_К_СДАЧЕ.md`](docs/05_ДОКУМЕНТАЦИЯ_К_СДАЧЕ.md).
