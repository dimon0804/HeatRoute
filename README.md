# HeatRoute

Сервис автоматического построения вариантов подключения перспективных ОКС
к существующей тепловой сети.

Конкурсный кейс «Сервис моделирования трасс подключения к тепловым сетям»,
«Лидеры цифровой трансформации» 2026.

На вход — один GeoJSON с существующей сетью, камерами, точками подключения ОКС
и пространственными ограничениями. На выходе — до трёх ранжированных вариантов новой
сети с маршрутами, местами присоединения, камерами, расходами, условными диаметрами
и полной стоимостью.

Решение приведено к техническому приложению **в редакции от 18.09**. Перечень отличий
от первой редакции и то, как каждое закрыто, — в
[`docs/08_ДЕЛЬТА_ТЗ_18.09.md`](docs/08_ДЕЛЬТА_ТЗ_18.09.md). Главное изменение: реконструкция
существующей сети выведена из расчётной модели, а состав выгрузки сокращён до четырёх
типов объектов.

## Быстрый старт

```bash
cp .env.example .env
docker-compose up -d --build
```

| Что | Адрес |
|---|---|
| Интерфейс с картой | http://localhost:3000 |
| Swagger UI | http://localhost:8080/swagger-ui.html |
| Состояние сервиса | http://localhost:8080/actuator/health |

Конкурсный набор — `data/samples/dataset_lct2026.geojson` (скорректированный датасет
от 18.09; прежний лежит в `data/samples/archive/`).
Готовый результат по нему, который требует раздел 7.2 ТЗ, лежит в
[`deliverable/`](deliverable/README.md): выгрузка обычного расчёта, выгрузка с учётом
глубины и ведомость объёмов работ.

### Разработка

```bash
cd backend  && mvn spring-boot:run -Dspring-boot.run.profiles=nodb   # без базы данных
cd backend  && mvn test                                              # 123 теста
cd frontend && npm run dev                                           # сервер разработки
cd frontend && npm run e2e                                           # 11 сквозных тестов в браузере
```

Сквозные тесты идут против поднятого стека: сначала `docker-compose up -d`.

Если локального JDK нет, сборка и тесты идут в контейнере с примонтированным
хранилищем зависимостей:

```bash
docker run --rm -v "$PWD/backend:/build" -v "$HOME/.m2:/root/.m2" -w /build \
    maven:3.8.8-eclipse-temurin-11 mvn -o -B test
```

Развёртывание с нуля — так, как его увидит чужая машина: клон репозитория, сборка
образов без кеша, подъём одной командой и сквозная проверка API и интерфейса.

```bash
bash ops/clean_room_check.sh
```

## Что реализовано

**Обязательный функционал (раздел 2.11 ТЗ)** — весь.

- Обработка всех точек подключения за один запуск; каждая точка — самостоятельная цель
  со своим расходом.
- Автоматический выбор места присоединения с применением правила 10 м: существующая
  камера, если она ближе десяти метров и число примыканий после подключения не превысит
  четырёх, иначе новая камера прямо в выбранной точке существующего участка.
- Определение совместного или раздельного подключения по расстоянию в графе.
- Соблюдение пространственных ограничений таблицы 2, включая специальные проходы,
  минимальные углы пересечения, минимальное горизонтальное расстояние при проходе рядом
  и запрет самопересечений трасс.
- Предел угла поворота 90°: слишком крутая вершина разбивается дугой снаружи поворота,
  а то, что разбить не удалось, попадает в счётчик и в журнал.
- Расчёт расходов и подбор условных диаметров по расходу и предельной длине, с тремя
  правилами раздела 2.3: диаметр не меняется посреди перегона между узлами смены расхода,
  не меняется ради нового отсчёта предельной длины и не уменьшается по направлению
  от точки подключения к месту присоединения.
- Предельная длина проверяется по каждому пути от места присоединения до точки
  подключения: общий ствол входит в каждый путь, параллельные ветви не складываются.
- Стоимость по разделу 6: новые участки, новые камеры и врезки в существующие камеры.
  Врезка 5 млн платится только за примыкание к существующей камере и за каждый новый
  участок, который в ней заканчивается.
- Сохранение частичного результата и штраф за точку без маршрута, с объяснением причины
  по каждой такой точке.
- До трёх содержательно отличающихся вариантов с ранжированием по `S`; если разбиений
  точек на три варианта не хватило, различие даёт форма сети — эвристика запускается
  с другого затравочного терминала.
- Выгрузка одним GeoJSON в составе раздела 7.1: участки, камеры, технические узлы
  и сводка по варианту, без Z-координат.

**Дополнительный режим с учётом глубины** — реализован, ранжируется отдельно, как требует
раздел 5: подбор глубины без дискретного шага, прохождение пересечений сверху или снизу
с выбором по стоимости, профиль с уклоном не круче 0,10 м/м, коэффициент `Kгл`, глубины
концов участков в выгрузке. Если манёвр не помещается, профиль возвращает замечание
маршрутизации: место пересечения запрещается и вариант строится заново.

**Сверх требований.**

- **Проверка любой выгрузки на соответствие приложению — внутри сервиса.**
  `GET /api/v1/jobs/{id}/compliance` проверяет свой расчёт,
  `POST /api/v1/compliance` — произвольную пару «выгрузка и входной набор». Отчёт
  называет правило, формулировку требования, объекты и то, что именно не сошлось.
  Ручка нужна не нам: департамент принимает такие расчёты от подрядчиков и сейчас
  проверяет их глазами. На нашей выгрузке это 2 815 сверок без нарушений, и число
  сверок в отчёте стоит рядом с числом нарушений намеренно: «нарушений нет» при нуле
  сверок ничего не значит. Правила берутся из подменяемого снаружи справочника,
  поэтому проверка работает и с другой редакцией приложения.
- **Независимая проверка выгрузки той же логикой, но другим кодом:**
  `tools/validate_result.py` переписывает правила заново, по тексту приложения,
  и сверяет с выгрузкой 1 916 значений. Совпадение двух независимых реализаций —
  довод; совпадение кода с самим собой — нет. Обе проверки нашли в нашей выгрузке
  два дефекта, которых не видел ни один из тестов: пустые значения глубины пропадали
  при записи в базу, а массив идентификаторов терял числовой тип.
- **Сертификат локальной оптимальности.** Главный вопрос к любой эвристике —
  «а вдруг рядом есть решение лучше». Сервис отвечает на него числом: на итоговом
  дереве лучшего варианта проверено **1 027 одиночных ходов** — перецепок ветвей
  и переносов развилок, — и ни один не улучшает решение. Гарантии глобального
  оптимума это не даёт и не может давать, но локальная оптимальность подтверждается
  проверкой, а не обещанием. Показатель отдаётся в сводке прогона вместе с числом
  вершин, не приведённых к пределу угла поворота.
- **Разбор трассы: почему труба пошла здесь.** `GET /api/v1/jobs/{id}/explain` для каждого
  участка называет ограничения рядом с ним, фактическое и требуемое расстояние, оставшийся
  запас, специальные проходы и во сколько участок длиннее прямой. Главное недоверие
  к автоматической трассировке звучит как «почему не прямее», и на конкурсном наборе
  ответ выходит буквальный: участок `new_v1_2` одним концом примыкает к существующей
  сети в месте присоединения, а с другой стороны его держит дом 83 — до границы его зоны
  отступа остаётся 0,11 м; `new_v1_4` длиннее прямой на 11 процентов, потому что обходит
  дом 105 с запасом 1,69 м. Разбор считается по готовой трассе, а не запоминается по ходу расчёта:
  запоминать пришлось бы для миллиона отвергнутых отрезков графа, из которых в решение
  попадут единицы.
- **Анализ чувствительности: что держит цену.** `GET /api/v1/jobs/{id}/sensitivity` решает
  задачу заново без каждой точки подключения по очереди и показывает её вклад в стоимость
  и протяжённость. Это численный эксперимент, а не вычитание длины отвода: убрав точку,
  эвристика перестраивает дерево целиком. На конкурсном наборе самая дорогая точка — №4:
  без неё решение дешевле на 27,3 млн руб. и короче на 182 м. Каждая точка — отдельное
  полное решение задачи, поэтому перебор всех семнадцати занимает около пяти минут,
  анализ вынесен в отдельную ручку и сам никогда не выполняется. Из интерфейса, кнопкой
  в разделе «Что держит цену», считаются три самые тяжёлые точки — это около минуты.
- **Запретные зоны**: щелчком по карте отмечается место, где копать нельзя, и сеть
  строится заново с этим условием.
- **Ведомость объёмов работ** отдельной выгрузкой: перечень участков и камер, свод
  по условным диаметрам и итог — таблица, которую открывают в Excel и по которой
  считают смету.
- **Перенос развилок в точку Ферма**: развилка ставится туда, где сумма стоимости
  примыкающих труб минимальна, а не в узел графа видимости.
- **Справочник через API** и подмена его файлом снаружи без пересборки.
- Набор с полным атрибутивным составом и тесты на нём, сквозные тесты интерфейса
  в браузере, проверка развёртывания с нуля.
- Поддержка типов ограничений сверх таблицы 2 через словарь псевдонимов: метро, школы,
  детские сады, больницы. Раздел 4 приложения называет это преимуществом при экспертном
  сравнении решений с сопоставимым качеством обязательной части.

## Соответствие требованиям к стеку

Раздел 3.2 ТЗ выдержан без отклонений: Java 11, `spring-boot-starter-parent:2.6.3`,
PostgreSQL, `springdoc-openapi-ui:1.7.0`, docker-compose, Ubuntu Server 22.

Предел по объёму входа проверен загрузкой, а не настройкой: файл 3 ГБ на 1 262 935
объектов принимается и разбирается за 98 с при куче 5,7 ГБ — меньшей, чем даёт
требуемая ТЗ машина. Набор для такой проверки собирает `tools/make_large_dataset.py`.

Входной файл до 3 ГБ обрабатывается потоково через временное дисковое хранилище;
выгрузка до 500 МБ пишется в поток ответа курсором по строкам базы.

Координаты, идентификаторы и конфигурация конкурсного набора нигде не зафиксированы
в коде (раздел 2.14 ТЗ, разъяснение №17). Справочник технического приложения вынесен
в `backend/src/main/resources/reference/heatroute-reference.yml` и подменяется
снаружи без пересборки:

```bash
java -jar heatroute.jar --spring.config.additional-location=file:/opt/heatroute/
```

## Как устроен расчёт

```
GeoJSON → разбор и восстановление данных → поле препятствий → граф видимости
        → разбиение точек и места присоединения → дерево Штейнера
        → расходы, диаметры и предельная длина → стоимость → ранжирование → GeoJSON
```

Ключевое решение — **граф видимости вместо сетки**. Кратчайший путь в нём состоит
из прямых отрезков и огибает препятствия по касательной, то есть даёт ту геометрию,
которую рисует инженер. Сеточный поиск при любом шаге даёт ступенчатую линию,
а её сглаживание рискует нарушить только что соблюдённые клиренсы.

Подробности — в [`docs/02_ALGORITHM.md`](docs/02_ALGORITHM.md)
и [`docs/05_ДОКУМЕНТАЦИЯ_К_СДАЧЕ.md`](docs/05_ДОКУМЕНТАЦИЯ_К_СДАЧЕ.md).
