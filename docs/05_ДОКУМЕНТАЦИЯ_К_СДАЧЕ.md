## 1. Алгоритм поиска маршрутов и совместного подключения ОКС

### 1.1. Общая схема

Расчёт идёт в шесть шагов. Каждый следующий пользуется результатом предыдущего
и ничего не знает о том, как тот получен.

```
Входной GeoJSON
      │
      ▼
[1] Разбор и восстановление данных        → нормализованная обстановка в метрах
      │
      ▼
[2] Свободное пространство                 → буферы препятствий по таблице 5.1
      │
      ▼
[3] Граф видимости                         → узлы и рёбра с приведённой длиной
      │
      ▼
[4] Разбиение ОКС и выбор точек врезки     → кандидаты вариантов
      │
      ▼
[5] Дерево Штейнера, расходы, диаметры     → участки сети
      │
      ▼
[6] Реконструкция, стоимость, ранжирование → до трёх вариантов
```

### 1.2. Свободное пространство

Для каждого пространственного ограничения с правилом «пересечение запрещено»
строится буфер

```
buffer = минимальное горизонтальное расстояние (таблица 5.1) + расчётная ширина пары труб / 2
```

Половина ширины добавляется потому, что нормативное расстояние отсчитывается между
внешними границами расчётных габаритов, а трасса на карте — это ось пары труб.

Ширина буфера зависит от условного диаметра, а диаметр становится известен только
после построения дерева. Граф строится один раз, поэтому клиренсы берутся по ДУ
магистрали — наибольшему, который может возникнуть в варианте. Маршрут, допустимый
для наибольшего диаметра, допустим и для любого меньшего, поэтому нарушение нормы
невозможно по построению, а не проверяется постфактум.

Буферы намеренно не объединяются в одну геометрию: раздельное хранение позволяет
исключить из проверки собственный контур подключаемого ОКС — труба заходит в своё
здание к ИТП, и для этой трассы её собственное здание препятствием не является.
Для всех прочих трасс оно остаётся зданием с полным клиренсом.

### 1.3. Граф видимости

Узлы графа:

| Категория | Откуда |
|---|---|
| Выпуклые вершины буферизованных контуров | опоры для огибания препятствий |
| Точки подключения перспективных ОКС | терминалы |
| Кандидаты точек врезки | см. 1.4 |

Ребро существует, если прямой отрезок между узлами не заходит внутрь запретной зоны.
Кратчайший путь в таком графе состоит из прямых отрезков и огибает препятствия
по касательной — это ровно та геометрия, которую рисует инженер. Сеточный поиск
при любом шаге даёт ступенчатую линию, которую потом приходится сглаживать,
рискуя нарушить клиренсы.

Берутся именно **выпуклые** вершины: кратчайший путь в плоскости с полигональными
препятствиями меняет направление только на них.

**Вес ребра — приведённая длина**, а не рубли:

```
w(e) = L(e) · Π Kспец(пересекаемые объекты со специальным проходом)
```

Стоимость метра одинакова вдоль всего пути с одним расходом, поэтому минимум
`Σ L·K` совпадает с минимумом `Σ L·c(ДУ)·K` при любом фиксированном ДУ. Так поиск
пути отделён от подбора диаметра, и одна матрица кратчайших путей переиспользуется
во всех итерациях.

Ребро отбрасывается, если пересекает объект со специальным проходом под углом меньше
требуемого (дороги и трамвайные пути — не менее 45°).

**Точка подключения — всегда конец ветви.** Транзит через чужую точку подключения
запрещён: он означал бы, что труба заходит в соседнее здание к его ИТП и выходит
обратно, а развилка при этом оказывается не в тепловой камере.

На конкурсном наборе граф содержит 3 544 узла и 123 007 рёбер; построение занимает
около 9 с в шестнадцать потоков.

### 1.4. Выбор точек врезки

Точка врезки — самое дорогое решение в задаче: она задаёт и длину новой трассы,
и объём реконструкции существующей сети до источника. Кандидаты формируются
по трём основаниям:

1. **Существующие тепловые камеры** с запасом по числу примыканий — врезка в них
   не требует строительства новой камеры;
2. **проекции точек подключения ОКС** на существующую сеть — ближайший выход
   для одного объекта;
3. **равномерная дискретизация сети** с шагом 25 м — места, выгодные для группы
   объектов, а не для одного.

К каждому кандидату сразу применяется правило 10 м раздела 8.2: если он не далее
десяти метров от существующей камеры и её степень позволяет — врезка выполняется
в камере; иначе в точке врезки строится новая.

Кандидатов получается около восьмидесяти. Строить дерево для каждого дорого, поэтому
они сначала оцениваются снизу — суммой расстояний в графе до терминалов группы, —
и полную проверку проходят двенадцать лучших. Оценка честная: дерево Штейнера
не короче наибольшего из этих расстояний и не длиннее их суммы.

### 1.5. Совместное подключение: разбиение ОКС

Кластеризация определяет, что подключается одной сетью, а что отдельно. Метрика —
расстояние **в графе маршрутизации**, а не по прямой: два здания через реку
геометрически рядом, а по трассе далеко.

Применяется агломеративная кластеризация по среднему расстоянию. Порождаются
разбиения от «все одной сетью» до трёх независимых частей; каждое даёт кандидата
в варианты, и лучшее определяется не заранее, а по итоговой стоимости.

Экономика подсказывает, что совместное подключение почти всегда выгоднее:
семнадцать отдельных врезок — это 85 млн руб. только за врезки плюс семнадцать
независимых трасс. Но выгоднее не всегда: врезка в дальнюю точку может потребовать
реконструкции существующей сети на всём пути к источнику, и тогда разделение
дешевле. На конкурсном наборе выиграло разделение на три части.

### 1.6. Построение дерева

Формально требуется дерево Штейнера с корнем в точке врезки и терминалами в точках
подключения. Задача NP-трудна, поэтому применяется эвристика кратчайшего пути
(Такахаси–Мацуяма):

1. дерево = корень;
2. находится не подключённый терминал, ближайший **ко всему дереву**;
3. кратчайший путь от него до дерева добавляется целиком, все вершины пути
   становятся узлами;
4. повторять, пока есть неподключённые терминалы.

Ветви, идущие в одну сторону, срастаются сами собой — это и есть совместное
подключение.

Порядок подключения меняет форму дерева, поэтому эвристика запускается **восемь раз**
с разными затравочными терминалами, и берётся лучшее дерево. Замеры на конкурсном
наборе: четыре запуска дают S = 14,671, восемь — 14,252, восемнадцать — тот же
результат за вдвое большее время.

**Ограничение на число примыканий к камере** (не более четырёх: один к источнику
и не более трёх в остальных направлениях) встроено в само построение, а не добавлено
постобработкой. Узел, исчерпавший предел, исключается и из источников поиска,
и из транзита. Предел учитывается с трёх сторон: у точки врезки часть мест занята
существующей сетью; у узлов дерева это родитель плюс три потомка; а если независимые
части варианта выбирают одну камеру, их примыкания суммируются.

**Ветвление через новую камеру на построенном участке.** Терминал часто
присоединяется прямым ребром графа, не добавляя промежуточных узлов, и дерево
упирается в предел примыканий, хотя место вокруг свободно. Физически это не тупик:
инженер ставит тепловую камеру на уже проложенной трубе и ветвится от неё. Сервис
делает то же самое — узел врезается в проекцию терминала на ближайший участок
дерева. Обе половины разрезанного участка лежат внутри исходного и проходимы
по построению, а отвод от новой камеры проверяется на клиренс отдельно.
Без этого приёма на наборе с полным атрибутивным составом один ОКС оставался
неподключённым при том, что в графе он достижим.

### 1.7. Расходы, диаметры, предельные длины

Расходы считаются снизу вверх: расход участка равен сумме расходов ОКС его поддерева.
Подающий и обратный трубопроводы имеют одинаковый расход, поэтому берётся расход
одной пары.

Для каждого участка выбирается минимальный условный диаметр, пропускная способность
которого не меньше расчётного расхода.

Предельная длина проверяется для непрерывной части сети одного ДУ. Тепловая камера
отсчёт не прерывает, смена диаметра — прерывает. При исчерпании предела диаметр
повышается на ступень, в точке смены ставится технический узел, отсчёт начинается
заново. Процесс сходится: повышение диаметра увеличивает и предел.

### 1.8. Качество геометрии

Три правила, каждое из которых проверяется автотестом на выгрузке:

**Спрямление.** Узлы графа видимости появляются на каждом обогнутом угле, и часть
из них после сборки дерева оказывается на одной прямой. Такие узлы удаляются,
но только если прямой отрезок между соседями проходим — срезанный угол не должен
нарушить клиренс.

**Запрет самопересечений** (раздел 2.3 ТЗ). Дерево не пересекается в графе, но
в плоскости две его ветви пересечься могут. В точке пересечения создаётся узел,
ребро одной ветви делится им на два, вторая переподчиняется этому узлу — ровно
то объединение, которого требует ТЗ. Пересечение исчезает, дерево остаётся деревом,
а сеть становится короче: пересечение само по себе означает, что часть пути
пройдена дважды. Если точка пересечения попадает вплотную к существующему узлу,
ветвь подключается к нему, иначе появлялись бы участки в сантиметры длиной.

Пересечения между **независимыми частями** сети объединением не лечатся: у каждой
своя точка врезки, и объединение дало бы два пути до одного ОКС вопреки разделу 2.2.
Такие разбиения ОКС отбрасываются целиком; разбиение «все одной сетью» пересечений
между частями не имеет по построению, поэтому пригодный вариант остаётся всегда.

**Отсутствие мелкой ломаной.** Звенья короче полуметра и участки, разбитые
на неоправданно большое число вершин, отлавливаются тестом.

**Отсечение ветвей без потребителей.** Перестроения могут оставить позади отросток,
который никуда не ведёт: расход по нему нулевой, диаметр подбирается наименьший,
но труба строится и стоит денег. Такие ветви удаляются. На конкурсном наборе
это убрало тупиковый участок 1,9 м и одну лишнюю камеру.

### 1.9. Реконструкция существующей сети

Дополнительный расход от каждой точки врезки распространяется по цепочке
`upstream_object_id` к источнику и складывается с существующим расходом каждого
затронутого участка. Расходы от разных врезок на общей части суммируются.

Если врезка выполнена **внутри** линейного участка, дополнительный расход действует
только на часть этого участка от точки врезки в сторону источника, и в выгрузку
идёт именно эта часть с фактической геометрией. Если на одном участке несколько
врезок, он делится ими на интервалы, и каждый несёт сумму расходов тех врезок,
что лежат дальше от источника.

```
Gитог = Gсущ + Gнов   →   ДУтреб = минимальный подходящий диаметр
ДУтреб ≤ ДУсущ → реконструкция не требуется
ДУтреб > ДУсущ → Cрек = Lрек · cрек(ДУтреб)
```

Для камеры, использованной под врезку, отдельно проверяется наибольший ДУ всех
примыкающих участков в итоговом варианте — с учётом новых и требуемых после
реконструкции. Превышение исходного ДУ камеры означает её реконструкцию,
учитываемую один раз независимо от числа врезок.

### 1.10. Ранжирование

```
S = 0,7 · C / 25 000 000 + 0,3 · L / 100
```

Содержательно совпадающие решения отсеиваются по отпечатку структуры — множеству
точек врезки и разбиению ОКС по частям сети. Небольшое смещение одной и той же
трассы отдельным вариантом не считается. Оставшиеся сортируются по возрастанию S,
первые три получают места 1, 2, 3.

## 2. Обработка ОКС, для которых маршрут не найден автоматически

Конкурсный набор подготовлен так, чтобы подключить можно было всех, и сервис
на нём подключает все семнадцать объектов. Тем не менее обратный случай обработан,
как требует раздел 2.9 ТЗ.

**Что происходит.** Построенная для остальных объектов часть результата сохраняется
полностью. ID проблемных объектов попадают в поле `unconnected_oks_ids` сводной
записи варианта, и за каждый начисляется штраф:

```
ШОКС = 100 000 000 + 500 000 · GОКС
```

**Причины, по которым объект может туда попасть**, и как они различаются:

| Причина | Когда возникает |
|---|---|
| Терминал недостижим в графе | точка подключения окружена препятствиями так, что прохода нужной ширины нет |
| Исчерпан предел примыканий | все допустимые узлы дерева заняты, новую ветвь привести некуда |
| Расход превышает справочник | расчётный расход ОКС больше пропускной способности наибольшего условного диаметра |
| Профиль по глубине не найден | в дополнительной задаче манёвр по глубине не вмещается в длину участка |

**Приоритет при выборе решения.** Порядок предпочтения кандидатов выстроен по цене
ошибки: сначала подключить все ОКС, затем не нарушать запрет пересечений трасс,
и только потом — дешевле. Неподключенный объект стоит не менее 100 млн руб. штрафа
и прямо ухудшает решение задачи, а пересечение трасс можно обойти другим разбиением,
поэтому жертвовать подключением ради него нельзя.

Отсутствие автоматически найденного маршрута не означает, что подключение технически
невозможно: это указание на место, требующее ручной проработки.

## 3. Описание выходных данных

Результат — один совмещённый файл GeoJSON типа `FeatureCollection` в WGS 84
(EPSG:4326). Все варианты лежат в одном массиве `features` и различаются
атрибутом `variant_id`.

У каждого типа объекта только свой обязательный набор атрибутов; поля чужих типов
не добавляются со значением `null`. Это отдельное требование раздела 10 ТП,
и оно проверяется автотестом на каждой сборке.

### 3.1. Состав выгрузки

| `object_type` | Геометрия | Что это |
|---|---|---|
| `heat_network` | LineString | участок новой тепловой сети |
| `tie_in` | Point | точка врезки в существующую сеть |
| `heat_network_reconstruction` | LineString | реконструируемая часть существующей сети |
| `heat_chamber` | Point | новая тепловая камера |
| `heat_chamber_reconstruction` | Point | реконструируемая существующая камера |
| `technical_node` | Point | технический узел в месте смены параметров |
| `depth_crossing` | Point | пересечение по глубине (только в дополнительной задаче) |
| `variant_summary` | `null` | сводная запись варианта, ровно одна на вариант |

### 3.2. Атрибуты по типам

**`heat_network`** — `id`, `object_type`, `variant_id`, `start_node_id`, `end_node_id`,
`flow_tph`, `diameter`, `length`, `laying_method`, `depth_start`, `depth_end`, `cost`.

`laying_method` принимает значение `base` для обычной прокладки и `special`
для специального прохода. `depth_start` и `depth_end` равны `null` в плоской задаче.

**`tie_in`** — `id`, `object_type`, `variant_id`, `existing_object_id`,
`existing_object_type`, `existing_diameter`, `required_diameter`, `cost`.

**`heat_network_reconstruction`** — `id`, `object_type`, `variant_id`,
`existing_object_id`, `existing_flow_tph`, `added_flow_tph`, `calculated_flow_tph`,
`existing_diameter`, `required_diameter`, `length`, `cost`.

**`heat_chamber`** — `id`, `object_type`, `variant_id`, `diameter`, `cost`.

**`heat_chamber_reconstruction`** — `id`, `object_type`, `variant_id`,
`existing_object_id`, `existing_diameter`, `required_diameter`, `cost`.

**`technical_node`** — `id`, `object_type`, `variant_id`.

**`depth_crossing`** — `id`, `object_type`, `variant_id`, `segment_id`, `utility_id`,
`utility_type`, `passage`, `new_depth`, `utility_depth`, `required_clearance`,
`actual_clearance`. Тип сверх раздела 10 ТП: его требует раздел 7 приложения
по глубине.

**`variant_summary`** — `id`, `object_type`, `variant_id`, `rank`,
`construction_cost`, `chamber_construction_cost`, `tie_in_cost`,
`reconstruction_cost`, `chamber_reconstruction_cost`, `unconnected_penalty`,
`calculated_cost`, `new_network_length`, `reconstruction_length`, `length`,
`score`, `unconnected_oks_ids`.

### 3.3. Связи между объектами

`start_node_id` и `end_node_id` участка ссылаются на точку врезки, тепловую камеру,
технический узел или точку подключения ОКС. Идентификаторы объектов входного файла —
существующих камер и точек подключения — раздел 10 повторно не выгружает, поэтому
часть ссылок разрешается против входного набора, а не против выгрузки. Автотест
проверяет, что **каждая** ссылка разрешается хотя бы в одном из двух.

Идентификаторы внутри варианта идут подряд без разрывов: `new_v2_1`, `new_v2_2`
и так далее. Это результат отдельной перенумерации — перебор кандидатов врезки
расходует идентификаторы, и без неё в выгрузке стояло бы `new_v2_1663`
при двадцати девяти участках.

### 3.4. Как получить

| Способ | Адрес |
|---|---|
| Интерфейс | кнопка «Выгрузить результат в GeoJSON» на панели вариантов |
| API | `GET /api/v1/jobs/{id}/result.geojson` |

Объекты читаются из базы курсором и пишутся в поток ответа по одному, поэтому

## 4. Алгоритм построения маршрута с учётом глубины

Дополнительная задача включается флагом `withDepth` в запросе на расчёт или
переключателем «с учётом глубины» в интерфейсе.

### 4.1. Модель

Поверхность земли условно горизонтальна, отметка `Z = 0`. Глубина измеряется
до верхней границы расчётного габарита новой сети; чем глубже, тем меньше `Z`.

Обычная глубина 3,0 м, минимальная 0,7 м, подбор с шагом 0,5 м. Габариты
существующих коммуникаций и их условные глубины берутся из таблицы 4.3;
для существующей тепловой сети габарит определяется по её условному диаметру
из таблицы 4.2.

### 4.2. Выбор прохождения

В месте пересечения новая сеть проходит выше или ниже коммуникации:

```
сверху: низ новой сети выше верха коммуникации на требуемый просвет
        h ≤ глубина коммуникации − просвет − высота габарита новой сети

снизу:  верх новой сети ниже низа коммуникации на требуемый просвет
        h ≥ глубина коммуникации + высота её габарита + просвет
```

Полученная глубина округляется к шагу 0,5 м в безопасную сторону — вверх для прохода
снизу, вниз для прохода сверху. Если справочник допускает оба варианта, берётся тот,
у которого коэффициент стоимости по глубине меньше.

**Пример с конкурсного набора.** Существующая тепловая сеть лежит на 3,0 м
до верха габарита, требуемый просвет 0,5 м. Проход сверху выводит новую сеть
на 2,0 м — там стоимость по глубине не растёт вовсе. Проход снизу потребовал бы
4,5 м и надбавки 15 % к стоимости участка. Выбран верхний, фактический просвет
получился 0,55–0,82 м при норме 0,5 м.

Для объектов с правилом «только под объектом» — дорог и трамвайных путей —
ограничение задаёт минимальную глубину, и обычные 3,0 м его перекрывают.

### 4.3. Профиль

Профиль состоит из участка изменения глубины, горизонтальной вставки в зоне
пересечения и возврата к обычной глубине. Уклон не круче 0,10 м/м: на изменение
глубины на метр требуется не менее десяти метров по горизонтали. Горизонтальная
вставка — 4 м, по 2 м с каждой стороны от точки пересечения.

```
  0 ┬──────────╮                      ╭──────────  поверхность Z = 0
    │           ╲                    ╱
2,0 │            ╰────────────────────╯            ← вставка 4 м над коммуникацией
    │           ↑ уклон ≤ 0,10 м/м   ↑
3,0 ┴───────────╯                    ╰───────────  обычная глубина
```

Если разбега на манёвр не хватает — участок короче требуемого, — профиль не строится
круче допустимого уклона. Участок отмечается как требующий ручной проработки,
и это видно в результате.

### 4.4. Стоимость

```
Kгл = 1 + 0,10 · (h − 3)   при h > 3,   иначе Kгл = 1
```

На наклонном участке зависимость линейна, поэтому берётся среднее арифметическое
коэффициентов концов. Пересечение отметки 3,0 м делит участок на две части
с раздельным расчётом, и в точке деления ставится технический узел.

### 4.5. Что попадает в результат

Глубина каждого участка в начале и в конце, Z-координаты всех вершин геометрии,
места пересечений с указанием прохождения сверху или снизу, фактические
и требуемые вертикальные расстояния, пересчитанная стоимость и перечень участков,
требующих ручной проработки.

Ранжирование вариантов после расчёта по глубине выполняется заново: стоимость
изменилась, и выигрывает тот вариант, у которого пересечений меньше или они дешевле.

## 5. Границы применения решения

### 5.1. Что не выполняется по условиям кейса

- Полный гидравлический расчёт: давление, потери напора, скорость теплоносителя,
  насосные режимы и балансировка сети. Вместо него — предельная длина непрерывной
  части одного условного диаметра.
- Расчёт и развитие мощности источника.
- Реальный рельеф, фактические высотные отметки коммуникаций, геология
  и грунтовые воды.
- Взаимные пересечения существующих коммуникаций между собой.
- Надземная прокладка; базовый способ — подземная бесканальная.
- Положение ИТП внутри здания.
- Изменение трассы существующей сети при реконструкции: используется существующая
  геометрия.
- Рабочее проектирование, расчёты прочности, компенсаторы, конструкция камер
  и специальных переходов.

### 5.2. Принятые допущения там, где входные данные молчат

Каждое допущение записывается в протокол разбора с кодом и списком затронутых
объектов и видно в интерфейсе и через API.

| Чего нет во входных данных | Что принято | Параметр |
|---|---|---|
| `upstream_object_id` | цепочка к источнику восстановлена обходом графа от источника | — |
| `flow_tph` у существующей сети | расход принят нулевым | `heatroute.ingest.existing-flow-mode` |
| `diameter` у тепловой камеры | наибольший ДУ примыкающих участков (правило 8.2 ТП) | — |
| полигоны `oks_future` | точка подключения работает самостоятельным ОКС | `allow-flow-on-connection-point` |
| точка подключения у `oks_future` | ближайшая к сети точка контура объекта | `derive-missing-connection-point` |
| тип ограничения вне таблицы 5.1 | разрешается через словарь псевдонимов; неизвестный обходится с зазором 1 м | `restriction-aliases` |

Отдельно: в конкурсном наборе все семнадцать точек подключения оказались **внутри**
полигонов-ограничений на 0,06–8,3 м от границы. Эти полигоны опознаны как контуры
самих подключаемых зданий. Без такого опознания собственное здание закрывает подход
к своей же точке буфером в пять метров, и маршрут не находится никогда.

### 5.3. Пределы метода

**Эвристика не гарантирует глобального оптимума.** Дерево Штейнера NP-трудно;
применяемая эвристика кратчайшего пути даёт результат не хуже удвоенного оптимума,
а восемь запусков с разными затравками сокращают разрыв на практике. Результат
воспроизводим: повторный расчёт на тех же данных даёт те же числа.

**Клиренс берётся по наибольшему диаметру варианта.** Это гарантирует соблюдение
нормы, но на плотной застройке может закрыть проход, которого хватило бы для тонкой
ветви. Переключается параметром `heatroute.routing.initial-design-dn`.

**Пересечение независимых частей сети приводит к отбрасыванию разбиения,
а не к перестроению ветви.** Вариант при этом не теряется: разбиение «все одной
сетью» пересечений между частями не имеет по построению.

**Плотность обстановки.** Граф видимости строится по вершинам буферизованных
контуров, и его размер растёт квадратично от их числа. На конкурсном наборе это
3 544 узла и 9 с построения. Если проверочный набор окажется на порядок плотнее,
граф заменяется навигационной сеткой по ограниченной триангуляции Делоне —
построение дерева работает с узлами и рёбрами и не знает, откуда они взялись.

### 5.4. Универсальность

Координаты, идентификаторы и конфигурация конкурсного набора нигде не зафиксированы
в коде (требование раздела 2.14 ТЗ).

Справочник технического приложения — таблицы 4.1, 4.2, 4.3, 5.1, 8.2 и параметры
разделов 6, 8, 9 — целиком вынесен в файл
`backend/src/main/resources/reference/heatroute-reference.yml` и подменяется снаружи
без пересборки:

```bash
java -jar heatroute.jar --spring.config.additional-location=file:/opt/heatroute/
```

Текущие значения справочника доступны через `GET /api/v1/reference` — по нему
значения сверяются с приложением построчно.

Зона проекции задана параметром `heatroute.geo.utm-zone`, а не константой: набор
из другого региона обрабатывается сменой параметра.

Обе ветки разбора — когда атрибуты во входных данных есть и когда их нет —
реализованы и покрыты тестами. Для проверки изготовлен набор с полным составом
атрибутов: скрипт `tools/make_full_dataset.py` достраивает конкурсный набор
до состава таблицы 2.2, а тест `FullSpecDatasetTest` доказывает, что на нём
не восстанавливается ничего — всё берётся из входных данных, и расчёт проходит
тем же кодом.
