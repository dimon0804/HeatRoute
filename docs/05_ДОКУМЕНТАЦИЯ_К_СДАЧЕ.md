## 1. Алгоритм поиска маршрутов и совместного подключения ОКС

### 1.1. Общая схема

Расчёт идёт в шесть шагов. Каждый следующий пользуется результатом предыдущего
и ничего не знает о том, как тот получен.

```
Входной GeoJSON
      │
      ▼
[1] Разбор и восстановление данных          → нормализованная обстановка в метрах
      │
      ▼
[2] Свободное пространство                  → буферы препятствий по таблице 2
      │
      ▼
[3] Граф видимости                          → узлы и рёбра с приведённой длиной
      │
      ▼
[4] Разбиение точек и места присоединения    → кандидаты вариантов
      │
      ▼
[5] Дерево Штейнера, расходы, диаметры       → участки сети
      │
      ▼
[6] Стоимость и ранжирование                 → до трёх вариантов
```

### 1.2. Свободное пространство

Для каждого пространственного ограничения с правилом «пересечение запрещено»
строится буфер

```
buffer = минимальное горизонтальное расстояние (таблица 2) + расчётная ширина пары / 2
```

Половина ширины добавляется потому, что расстояние по разделу 3.1 отсчитывается
до **внешней границы расчётного габарита** новой сети, а линия в GeoJSON — это ось
пары труб.

Ширина буфера зависит от условного диаметра, а диаметр становится известен только
после построения дерева. Граф строится один раз, поэтому клиренсы берутся по ДУ
магистрали — наибольшему, который может возникнуть в варианте. Маршрут, допустимый
для наибольшего диаметра, допустим и для любого меньшего, поэтому нарушение нормы
невозможно по построению, а не проверяется постфактум. На конкурсном наборе расчётный
ДУ клиренсов — 400 мм.

Буферы намеренно не объединяются в одну геометрию: раздельное хранение позволяет
исключить из проверки собственный полигон подключаемой точки. Раздел 2.2 приложения
это прямо разрешает: для полигона, содержащего целевую `oks_connection_point`,
допускается один финальный прямой участок от ближайшей границы до точки, и требование
отступа к своему полигону на него не распространяется. Для всех прочих трасс тот же
полигон остаётся препятствием с полным клиренсом.

С 18.09 в таблице 2 появилась отдельная строка «Железная дорога (`railway`) —
пересечение запрещено, 1,0 м». До этого железной дороги в таблице не было, и сервис
относил её к трамвайным путям как к ближайшему рельсовому типу, то есть пересекал
специальным проходом. Теперь `railway` — непроходимое ограничение, и псевдоним
на трамвайные пути из справочника убран.

### 1.3. Граф видимости

Узлы графа:

| Категория | Откуда |
|---|---|
| Выпуклые вершины буферизованных контуров | опоры для огибания препятствий |
| Точки подключения ОКС | терминалы |
| Кандидаты мест присоединения | см. 1.4 |

Ребро существует, если прямой отрезок между узлами не заходит внутрь запретной зоны.
Кратчайший путь в таком графе состоит из прямых отрезков и огибает препятствия
по касательной — это ровно та геометрия, которую рисует инженер. Сеточный поиск
при любом шаге даёт ступенчатую линию, которую потом приходится сглаживать, рискуя
нарушить клиренс; а раздел 2.1 приложения отдельной фразой запрещает «необоснованные
мелкие изломы, зигзаги и ступенчатые фрагменты».

Берутся именно **выпуклые** вершины: кратчайший путь в плоскости с полигональными
препятствиями меняет направление только на них.

**Вес ребра — приведённая длина**, а не рубли:

```
w(e) = L(e) · max Kспец(пересекаемые объекты со специальным проходом)
```

Стоимость метра одинакова вдоль всего пути с одним расходом, поэтому минимум
`Σ L·K` совпадает с минимумом `Σ L·c(ДУ)·K` при любом фиксированном ДУ. Так поиск
пути отделён от подбора диаметра, и одна матрица кратчайших путей переиспользуется
во всех итерациях. Берётся именно наибольший коэффициент, а не произведение:
разъяснение №8 говорит, что при наложении специальных проходов коэффициенты
не суммируются и не перемножаются.

Ребро отбрасывается, если пересекает объект со специальным проходом под углом меньше
требуемого: для дорог и трамвайных путей — не менее 45°. Угол считается относительно
линии ограничения для линейной геометрии и в точке входа относительно границы
полигона — для полигональной (разъяснение №6).

На конкурсном наборе граф содержит **3 545 узлов и 96 027 рёбер**.

### 1.4. Выбор места присоединения

Место присоединения — самое дорогое решение в задаче: оно задаёт длину всей новой
трассы и определяет, обойдётся ли вариант новой камерой или врезками. Кандидаты
формируются по трём основаниям:

1. **существующие тепловые камеры** с запасом по числу примыканий;
2. **проекции точек подключения** на существующую сеть — ближайший выход
   для одного объекта;
3. **равномерная дискретизация существующей сети** с шагом 25 м — места, выгодные
   для группы точек, а не для одной.

К каждому кандидату применяется правило раздела 2.4: если кандидат не далее десяти
метров от существующей камеры **и** после подключения к ней будет примыкать не более
четырёх линейных участков, используется эта камера, и каждый новый участок,
заканчивающийся в ней, стоит 5 млн руб. врезки. Иначе новая камера ставится прямо
в выбранной точке существующего участка, отдельный объект места присоединения
не формируется, а присоединение входит в стоимость камеры. Если условию отвечают
несколько существующих камер, приложение разрешает выбрать любую; сервис берёт
ближайшую с запасом по примыканиям.

Примыкания считаются по правилу, которое 18.09 изменилось: **каждый линейный участок,
геометрически заканчивающийся в камере, — отдельное примыкание, а существующая линия,
проходящая через камеру и разделённая ею на две части, занимает два места из четырёх.**
Старое правило формулировалось асимметрично («один участок к источнику и не более
трёх в остальных направлениях») и давало другой счёт. Транзитная степень существующих
камер восстанавливается при разборе и попадает в протокол записью
`chamber.transitDegree` — без неё сервис считал бы свободными места, которых нет.

Это правило видно на результате. Новая камера `ch_v1_13`, поставленная в участок 126,
имеет ровно четыре примыкания: два — половины разрезанного ею существующего участка,
два — новые участки `new_v1_1` и `new_v1_2`. Пятый участок в неё не влез бы, и поиск
это учитывал ещё при построении дерева, а не обнаружил постфактум.

Кандидатов на конкурсном наборе получается **78**. Строить дерево для каждого дорого,
поэтому они сначала оцениваются снизу — суммой расстояний в графе до терминалов
группы, — и полную проверку проходят двенадцать лучших. Оценка честная: дерево
Штейнера не короче наибольшего из этих расстояний и не длиннее их суммы.

### 1.5. Совместное подключение: разбиение точек

Кластеризация определяет, что подключается одной сетью, а что отдельно. Метрика —
расстояние **в графе маршрутизации**, а не по прямой: два здания через реку
геометрически рядом, а по трассе далеко.

Применяется агломеративная кластеризация по среднему расстоянию. Порождаются
разбиения от «все одной сетью» до трёх независимых частей; каждое даёт кандидата
в варианты, и лучшее определяется не заранее, а по итоговому показателю.

Единицей задачи служит **точка подключения, а не полигон ОКС**: разъяснение №4
говорит, что каждая `oks_connection_point` — самостоятельная цель со своим расходом,
а отдельная связь точки с полигоном не требуется. Полигон участвует в расчёте только
как препятствие. Это упрощение по сравнению с первой редакцией, где точки надо было
группировать по объектам капитального строительства.

Экономика подсказывает, что совместное подключение обычно выгоднее: каждое лишнее
место присоединения стоит целой камеры, а параллельные трассы дублируют метры. Но
выгоднее не всегда, поэтому решает счёт: на конкурсном наборе одна общая сеть
выиграла у двух и трёх частей (раздел 0).

### 1.6. Построение дерева

Формально требуется дерево Штейнера с корнем в месте присоединения и терминалами
в точках подключения. Задача NP-трудна, поэтому применяется эвристика кратчайшего
пути (Такахаси–Мацуяма):

1. дерево = корень;
2. находится не подключённый терминал, ближайший **ко всему дереву**;
3. кратчайший путь от него до дерева добавляется целиком, все вершины пути
   становятся узлами;
4. повторять, пока есть неподключённые терминалы.

Ветви, идущие в одну сторону, срастаются сами собой — это и есть совместное
подключение.

Порядок подключения меняет форму дерева, поэтому эвристика запускается восемь раз
с разными затравочными терминалами, и берётся лучшее дерево. Число затравок —
параметр `heatroute.routing.steiner-restarts`; восемь выбрано по замеру на прежней
редакции модели, после перехода на редакцию 18.09 замер не повторялся, поэтому
числа того замера в документе не приводятся.

**Предел примыканий встроен в само построение**, а не добавлен постобработкой. Узел,
у которого четыре места заняты, исключается и из источников поиска, и из транзита.
Предел учитывается с трёх сторон: у места присоединения часть мест занята существующей
сетью; у узлов дерева это родитель плюс потомки; а если независимые части варианта
выбирают одну камеру, их примыкания суммируются.

**Разветвления возможны только в тепловых камерах** (раздел 2.1). Поворот без смены
параметров остаётся вершиной линии и узла не получает; технический узел ставится
только там, где без разветвления кончается один участок и начинается другой из-за
смены способа прокладки или профиля глубины. Поэтому в лучшем варианте технических
узлов нет вовсе: специальных проходов в нём нет, а расчёт двумерный.

**Ветвление через новую камеру на построенном участке.** Терминал часто присоединяется
прямым ребром графа, не добавляя промежуточных узлов, и дерево упирается в предел
примыканий, хотя место вокруг свободно. Физически это не тупик: инженер ставит камеру
на уже проложенной трубе и ветвится от неё. Сервис делает то же — узел врезается
в проекцию терминала на ближайший участок дерева. Обе половины разрезанного участка
лежат внутри исходного и проходимы по построению, а отвод от новой камеры проверяется
на клиренс отдельно. Без этого приёма на наборе с полным атрибутивным составом одна
точка оставалась неподключённой при том, что в графе она достижима.

### 1.6.1. Локальное улучшение дерева

Эвристика подключает объекты по одному и назад не оглядывается: ветвь, проложенная
третьей, могла бы идти иначе, если бы знала о пятой. Поэтому по готовому дереву идёт
проход, который пробует перецепить каждую ветвь в место, ставшее удобным позже:
к существующему узлу либо к точке на участке, где тогда ставится тепловая камера.

Критерий приёма хода — **денежный, а не «короче»**. Первая версия принимала любое
укорочение и платила за него лишними камерами: тепловая камера стоит как 25–40 метров
трубы в зависимости от диаметра, поэтому новая развилка оправдана только тогда, когда
экономит больше, чем стоит сама.

### 1.6.2. Перенос развилок в точку Ферма

Развилки дерева стоят там, где сошлись два кратчайших пути в графе видимости, —
обычно на углу обогнутого здания. Оптимальная развилка трёх ветвей лежит в точке
Ферма, где рёбра расходятся под 120°; разница между остовным деревом и деревом
Штейнера берётся в основном здесь.

Минимизируется стоимость, а не длина: `Σ wᵢ · |x − pᵢ|`, где `wᵢ` — цена метра трубы
соответствующего ДУ. Ствол тянет развилку сильнее отводов, потому что его метр дороже.
Точка ищется алгоритмом Вейсфельда, затем проверяется проходимость каждого нового
отрезка. Если оптимум лежит внутри препятствия, пробуется частичный сдвиг к нему:
функция стоимости на этом отрезке выпуклая, и первая проходимая доля пути — лучшая
из достижимых.

Ход добавлен потому, что без него увеличение числа попыток вдесятеро не меняло
результат вовсе: поиск стоял в локальном оптимуме, и не хватало именно хода,
а не времени. Насколько он выигрывает на редакции 18.09, отдельно не замерялось.

### 1.7. Предел угла поворота

Приложение в редакции 18.09 ввело геометрическое ограничение, которого раньше
не было:

> «Угол поворота определяется как изменение направления относительно продолжения
> предыдущего участка: 0° соответствует движению по прямой. Допускается произвольный
> угол поворота до 90° включительно. Отдельное удорожание поворота не применяется.»

Это не вопрос стоимости, а вопрос допустимости. Граф видимости огибает препятствие
по касательным и на остром выступе способен дать поворот круче 90°: путь буквально
разворачивается вокруг вершины препятствия. Такую вершину нельзя ни срезать,
ни сгладить внутрь — там препятствие. Поэтому поворот разбивается **наружу**: вершина
заменяется короткой дугой того же радиуса вокруг неё, и один крутой поворот становится
несколькими мелкими. Точки дуги лежат дальше от препятствия, чем исходная вершина,
поэтому клиренс от него только растёт; но рядом может оказаться другое препятствие,
поэтому каждое новое звено проверяется на проходимость, а радиус при неудаче
уменьшается.

Радиус ограничен снизу: ниже полуметра звенья дуги сами становятся той «мелкой
ломаной», которую приложение запрещает. Если привести вершину к пределу не удалось,
она остаётся как была и попадает в счётчик нарушений и в журнал: тихо отдать трассу
с недопустимым поворотом хуже, чем показать, что здесь предел не выдержан.

На конкурсном наборе предел выдержан во всех трёх вариантах без остатка. Наибольший
поворот внутри участка лучшего варианта — **89,6°**, то есть решение стоит вплотную
к границе и за неё не выходит. Это же проверяет независимая проверка выгрузки
(раздел 3.3.2), считая угол в каждой внутренней вершине каждой линии.

### 1.8. Расходы, диаметры, предельные длины

Расходы считаются снизу вверх: расход участка равен сумме расчётных расходов всех
точек подключения, расположенных далее по этому участку. Подающий и обратный
трубопроводы имеют одинаковый расход, поэтому берётся расход одной пары, а не сумма
(раздел 2.1).

Для каждого участка выбирается минимальный по таблице 1 диаметр, пропускная
способность которого не меньше расчётного расхода. Дальше действуют четыре правила
раздела 2.3, три из которых 18.09 были сформулированы заново:

| Правило | Как соблюдается |
|---|---|
| Если минимальный по расходу ДУ не проходит по предельной длине — берётся следующий, удовлетворяющий обоим условиям | повышение на ступень с повторной проверкой; процесс сходится, потому что рост ДУ увеличивает и предел |
| На пути между узлами смены расхода выбранный ДУ сохраняется на всей длине | сеть разбирается на перегоны между узлами смены расхода, диаметр назначается перегону целиком, а не участку выгрузки |
| Менять ДУ только ради нового отсчёта предельной длины нельзя; произвольное завышение не допускается | диаметр повышается единственной причиной — расходом или исчерпанным пределом; отдельный инвариант проверяет, что каждый выбранный ДУ минимален из допустимых |
| **По направлению от точки подключения к месту присоединения ДУ не должен уменьшаться** | после назначения диаметров идёт проход, приводящий последовательность к монотонной; инвариант проверяется тестом и независимой проверкой выгрузки |

Монотонность — новый инвариант редакции 18.09. Он не следует из расчёта расходов
автоматически: расход по направлению к месту присоединения растёт, но повышение
диаметра из-за предельной длины может случиться на отводе, а не на стволе, и тогда
на стыке диаметр формально уменьшается. На конкурсном наборе последовательность
монотонна на каждом пути: например, на самом длинном пути лучшего варианта
диаметры идут 150 → 200 → 250 → 300 к месту присоединения.

**Предельная длина проверяется по каждому непрерывному пути**, а не по «непрерывной
части сети», как читалось раньше:

> «Предельная длина проверяется отдельно по каждому непрерывному пути. Общий участок
> разветвлённой сети учитывается в каждом соответствующем пути. Длины параллельных
> ветвей между собой не суммируются. Камера или технический узел без изменения
> условного диаметра новый отсчёт не начинают.»

Сервис обходит дерево от места присоединения к каждой точке подключения и накапливает
длину непрерывного участка одного диаметра; общий ствол входит в каждый путь, ветви
между собой не складываются. Смена диаметра начинает новый отсчёт, камера и технический
узел — нет.

На конкурсном наборе предел не исчерпан с запасом: самый длинный путь от места
присоединения до точки подключения — **662,1 м**, а предельная длина наименьшего
использованного на этом пути диаметра (ДУ 150) — 696 м. То есть путь целиком короче
предела даже самой тонкой своей части, и повышать диаметр ради предельной длины
не пришлось ни на одном пути.

### 1.9. Качество геометрии

**Спрямление.** Узлы графа видимости появляются на каждом обогнутом угле, и часть
из них после сборки дерева оказывается на одной прямой. Такие узлы удаляются,
но только если прямой отрезок между соседями проходим — срезанный угол не должен
нарушить клиренс.

**Запрет самопересечений** (раздел 2.1 приложения, раздел 2.3 ТЗ). Дерево
не пересекается в графе, но в плоскости две его ветви пересечься могут. В точке
пересечения создаётся узел, ребро одной ветви делится им на два, вторая
переподчиняется этому узлу. Пересечение исчезает, дерево остаётся деревом, а сеть
становится короче: пересечение само по себе означает, что часть пути пройдена дважды.
Если точка пересечения попадает вплотную к существующему узлу, ветвь подключается
к нему, иначе появлялись бы участки в сантиметры длиной. Поскольку разветвление
допустимо только в камере, новый узел — это тепловая камера со своей стоимостью
по таблице раздела 3.2.

Пересечения между **независимыми частями** сети объединением не лечатся: у каждой
своё место присоединения, и объединение дало бы два пути до одной точки вопреки
разделу 2.1. Поэтому часть, пересекающая уже принятые, строится заново — с принятыми
участками в роли препятствия наравне со зданиями. Обход соседней части почти всегда
дешевле, чем потеря разбиения. Если обхода нет вовсе, разбиение отбрасывается;
разбиение «все одной сетью» пересечений между частями не имеет по построению, поэтому
пригодный вариант остаётся всегда.

**Отсутствие мелкой ломаной.** Звенья короче полуметра и участки, разбитые
на неоправданно большое число вершин, отлавливаются тестом.

**Отсечение ветвей без потребителей.** Перестроения могут оставить позади отросток,
который никуда не ведёт: расход по нему нулевой, диаметр подбирается наименьший,
но труба строится и стоит денег. Такие ветви удаляются.

### 1.10. Клиренсы: по трубе, а не по магистрали

Минимальное расстояние до препятствия зависит от габарита трубы, а габарит — от
условного диаметра. Диаметр у разных частей сети разный: ствол у места присоединения
несёт суммарный расход, отвод к одной точке — только её собственный.

Граф видимости строится по диаметру магистрали, потому что строится один раз. Но
каждый отрезок, которого в графе нет — отвод от новой камеры, перецепленная ветвь,
перенесённая развилка, дуга приведения угла, — проверяется по диаметру **своей**
трубы. Это не ослабление проверки: автотест на клиренсы берёт диаметр из выгрузки
и проверяет каждое звено каждого участка по нему. Ослабить было бы легко, а тест
бы не заметил — поэтому он и написан по фактическим диаметрам, а не по расчётному.

### 1.10.1. Минимальное расстояние при проходе рядом

Разъяснение №7 и раздел 4 приложения разделили два случая, которые раньше читались
как один:

> «Минимальное горизонтальное расстояние применяется при прохождении рядом с объектом.
> Внутри разрешённого специального пересечения оно не проверяется.»

То есть дорогу пересечь можно, а идти вдоль неё в полутора метрах — нельзя. Различить
это по признаку «пересекает или нет» не получается, и выяснилось это на конкурсном
наборе: существующая тепловая сеть сама относится к специальным объектам с отступом
1 м, а новая сеть обязана к ней присоединиться. Отрезок, выходящий из места
присоединения, лежит внутри её метровой зоны, и первая версия проверки сделала
недостижимыми все семнадцать точек.

Правило переписано на **длину хода внутри зоны отступа**: выход из места присоединения
задевает зону на считанные метры, а проход вдоль объекта тянется в ней долго. Порог —
ключ `heatroute.routing.special-alongside-tolerance-m`, по умолчанию 3 м. Это
эвристика, и она названа эвристикой: приложение численного критерия «рядом»
не задаёт, поэтому граница вынесена в настройку, а не спрятана в код.

### 1.11. Стоимость

```
обычный участок:      Cуч = L · cнов(ДУ) · Kгл
специальный участок:  Cуч = L · cнов(ДУ) · Kгл · Kспец
```

`L` — длина по горизонтальной проекции в EPSG:32637. Если параметры меняются
по длине, части считаются отдельно; на границах специального прохода и на отметке
3,0 м участок делится, и в месте деления появляется технический узел, если там нет
камеры или точки подключения.

```
Cстр = Σ Cуч + Σ Cкамер + 5 000 000 · (число новых участков, заканчивающихся
                                       в существующих камерах)
Ш    = 100 000 000 + 500 000 · G      за каждую неподключённую точку подключения
Cитог = Cстр + Σ Ш
```

Диаметр и стоимость новой камеры определяются по **наибольшему ДУ всех примыкающих
к ней участков**, включая существующие. Это видно на результате: камера `ch_v1_13`
получила ДУ 400 и стоимость 5 млн руб., хотя наибольший новый участок в ней —
ДУ 300; четыреста дал существующий участок 126, который она разделила.

Два правила редакции 18.09, которые легко нарушить в обратную сторону:

- стоимость новой камеры **включает** присоединение к существующей сети, отдельная
  врезка при строительстве новой камеры не добавляется;
- врезка 5 млн руб. считается **за каждый новый участок**, заканчивающийся
  в существующей камере, а не за место присоединения. Два участка, пришедших в одну
  существующую камеру, — это две врезки.

Штраф считается за **точку подключения**, а не за объект капитального строительства:
в новой редакции каждая точка самостоятельна и имеет собственный расход.

### 1.12. Ранжирование

```
S = 0,7 · C / 25 000 000 + 0,3 · L / 100
```

`C` — итоговая стоимость варианта, `L` — **суммарная длина новых участков**. В первой
редакции в `L` входили ещё и реконструируемые части; теперь только новое
строительство.

Содержательно совпадающие решения отсеиваются по отпечатку структуры — множеству
мест присоединения и разбиению точек по частям сети. Небольшое смещение одной и той
же трассы отдельным вариантом не считается (раздел 6). Оставшиеся сортируются
по возрастанию `S`, первые три получают места 1, 2, 3.

Если разных пар «место присоединения + разбиение» набралось меньше трёх, включается
запасной источник различий: эвристика запускается принудительно с другого затравочного
терминала и строит при том же месте присоединения сеть другой формы. Это нужно
на наборе, где все точки лежат одной гроздью и разбиение единственное, — иначе
«до трёх вариантов» раздела 2.11 ТЗ не выполнить. Затравочный вариант принимается
только при том же числе подключённых точек. На конкурсном наборе запас не тратится:
три разбиения дают три разные пары сами.

Режимы **не сводятся в одно ранжирование**. Раздел 5 приложения требует считать
вариант с глубиной отдельным набором и отдельным файлом, и сервис так и делает:
двумерный расчёт даёт свои три места, глубинный — свои. Это не формальность:
на конкурсном наборе лидеры двух режимов разные (раздел 4.5).

## 2. Обработка точек подключения, для которых маршрут не найден автоматически

Конкурсный набор подготовлен так, чтобы подключить можно было всех, и сервис
на нём подключает все семнадцать точек. Тем не менее обратный случай обработан,
как требует раздел 2.9 ТЗ.

**Что происходит.** Построенная для остальных точек часть результата сохраняется
полностью. Идентификаторы проблемных точек попадают в поле `unconnected_oks_ids`
сводной записи варианта, и за каждую начисляется штраф:

```
Ш = 100 000 000 + 500 000 · G
```

Тип идентификатора сохраняется таким же, как во входных данных, — это отдельное
требование раздела 7.2: если на входе пришло число, в массиве стоит число, а не
строка. Сырое значение идентификатора запоминается при разборе и не приводится
к внутреннему строковому виду.

**Отказ от подключения только вынужденный.** Разъяснение №15 закрывает лазейку:
намеренно не подключить точку ради лучшего показателя нельзя. Арифметика к этому
и не подталкивает — штраф от 100 млн руб. дороже любой трассы на этом наборе, —
но порядок предпочтения кандидатов выстроен явно по цене ошибки: сначала подключить
все точки, затем не нарушить запрет пересечений трасс, и только потом — дешевле.
Вариант с меньшим числом подключённых точек не может обойти вариант с большим,
как бы ни сложилась стоимость.

**Причина приходит вместе с идентификатором** — в поле `unconnectedReasons` сводки
варианта и в панели интерфейса. Список идентификаторов без объяснения бесполезен:
обработать случай — значит сказать, что именно с объектом не так. Причина известна
ровно там, где объект выбывает, и доносится оттуда до экрана.

| Причина | Когда возникает |
|---|---|
| Точка подключения недостижима: от неё нет ни одного допустимого отрезка до остальной обстановки | точка со всех сторон закрыта ограничениями, и узла в графе для неё не нашлось |
| Маршрут не найден: нет пути по клиренсу расчётного диаметра либо у всех допустимых узлов исчерпан предел примыканий | узел есть, но дерево до него не доходит; сервис не утверждает, что именно помешало, потому что различить это стоило бы отдельного перебора |
| Не нашлось допустимого места присоединения | к кандидатам нет пути либо у всех исчерпан предел примыканий |
| Расход превышает пропускную способность наибольшего ДУ таблицы 1 | расчётный расход больше 22 501,9 т/ч |

Контракт выгрузки это не меняет: раздел 7.2 задаёт состав атрибутов, и объяснение
там было бы лишним полем. Приложение разрешает дополнительные свойства, но текстовое
объяснение на карте бесполезно, поэтому оно живёт в API, который читает интерфейс.

Отсутствие автоматически найденного маршрута не означает, что подключение технически
невозможно: это указание на место, требующее ручной проработки.

## 2б. Запретные зоны

Сверх требований кейса. Отвечает на вопрос, который возникает при обсуждении любой
трассы первым: «а если здесь копать нельзя?». Стройплощадка, охранная зона, участок,
который город не отдаёт, — всё это появляется позже входных данных и в них не описано.

Зона задаётся щелчком по карте: центр и радиус. Для расчёта она работает как обычное
препятствие, но в граф видимости не попадает — граф строится один раз на расчёт,
а запреты меняются от запуска к запуску, поэтому зона действует маской разрешённых
рёбер графа.

Это не правка результата руками, запрещённая разделом 2.12 ТЗ: геометрию строит
расчёт, и целиком заново. Зона — дополнительное исходное условие.

Если обхода нет, соответствующие точки попадают в список неподключённых со штрафом
и с причиной. В API — поле `forbiddenZones` запроса `POST /api/v1/jobs`.

## 3. Описание выходных данных

Результат **каждого режима** — отдельный файл GeoJSON типа `FeatureCollection`
в WGS 84 (EPSG:4326). Все варианты режима лежат в одном массиве `features`
и различаются атрибутом `variant_id`. Двумерный и глубинный расчёты дают два файла
и не смешиваются.

У каждого типа объекта только свой набор атрибутов; поля чужих типов не добавляются
со значением `null`. Приложение разрешает дополнительные свойства и при проверке
обязательной части их игнорирует, но **лишних типов объектов оно не предусматривает**,
поэтому в выгрузке ровно четыре типа и ничего больше.

### 3.1. Состав выгрузки

| `object_type` | Геометрия | Что это |
|---|---|---|
| `heat_network` | LineString | участок новой тепловой сети |
| `heat_chamber` | Point | новая тепловая камера |
| `technical_node` | Point | технический узел в месте смены параметров участка |
| `variant_summary` | `null` | сводная запись варианта, ровно одна на вариант |

Что убрано по сравнению с первой редакцией и почему:

| Было | Почему нет |
|---|---|
| `tie_in` | «Отдельный объект `tie_in` не формируется» (разъяснение №13), «отдельный геообъект места присоединения не формируется» (п. 2.4). Место присоединения видно как новая камера либо как конец участка в существующей камере, а деньги за врезки — в сводке |
| `heat_network_reconstruction`, реконструируемая камера | реконструкции в модели нет |
| `depth_crossing` | тип сверх состава раздела 7.1; вертикаль задаётся атрибутами `depth_start` / `depth_end`, а разбор пересечений остался в API и в ведомости |
| Z-координаты вершин | «Z-координаты в GeoJSON не требуются» (раздел 5). Проверка выгрузки отдельно следит, что в координатах ровно две компоненты |

### 3.2. Атрибуты по типам

Состав — по таблице раздела 7.2 приложения.

**`heat_network`** — `id`, `object_type`, `variant_id`, `start_node_id`, `end_node_id`,
`flow_tph`, `diameter`, `length`, `laying_method`, `depth_start`, `depth_end`, `cost`.

`laying_method` принимает значение `base` для обычного участка и `special`
для специального прохода. `length` — длина по горизонтальной проекции. `depth_start`
и `depth_end` равны `null` в базовом двумерном режиме.

**`heat_chamber`** — `id`, `object_type`, `variant_id`, `diameter`, `cost`. Сверх
требований добавлено свойство `degree` — число примыкающих линейных участков при
пределе четыре. Это дополнительное свойство в смысле раздела 7, и оно добавлено
намеренно: правило четырёх примыканий проверяется по геометрии, и читающему выгрузку
полезно видеть счёт, а не пересчитывать его сам.

**`technical_node`** — `id`, `object_type`, `variant_id`. Обязательных атрибутов сверх
общих приложение не задаёт.

**`variant_summary`** — `id`, `object_type`, `variant_id`, `rank`, `construction_cost`,
`chamber_construction_cost`, `existing_chamber_tie_in_count`,
`existing_chamber_tie_in_cost`, `unconnected_penalty`, `calculated_cost`,
`new_network_length`, `score`, `unconnected_oks_ids`.

Состав сводки 18.09 изменился: `tie_in_cost` переименован
в `existing_chamber_tie_in_cost`, добавлено `existing_chamber_tie_in_count`, удалены
`reconstruction_cost`, `chamber_reconstruction_cost`, `reconstruction_length`
и `length`. Суммарная длина теперь одна — `new_network_length`, и именно она входит
в показатель.

### 3.3. Связи между объектами

`start_node_id` и `end_node_id` участка ссылаются на тепловую камеру (новую или
существующую), технический узел или точку подключения ОКС. Отдельное требование
раздела 7.2: эти узлы должны совпадать с **геометрическими концами** LineString.
Поворот без смены параметров остаётся внутренней вершиной линии и узла не получает —
поэтому в выгрузке участки длиной в десятки метров содержат по нескольку вершин,
и это не ошибка, а прямое следование правилу.

Идентификаторы объектов входного файла — существующих камер и точек подключения —
раздел 7 повторно не выгружает, поэтому часть ссылок разрешается против входного
набора, а не против выгрузки. Автотест проверяет, что **каждая** ссылка разрешается
хотя бы в одном из двух.

Идентификаторы внутри варианта идут подряд без разрывов: `new_v2_1`, `new_v2_2`
и так далее. Это результат отдельной перенумерации — перебор кандидатов места
присоединения расходует идентификаторы, и без неё в выгрузке стояли бы
четырёхзначные номера при двадцати девяти участках.

### 3.3.1. Ведомость объёмов работ

Сверх требований кейса. Выгрузка GeoJSON адресована ГИС, а смету по ней никто считать
не будет: сметчику нужен перечень строк, который открывается в Excel и складывается.

`GET /api/v1/jobs/{id}/statement.csv?variantCode=v1` — таблица по одному варианту:

| Раздел | Что в нём |
|---|---|
| шапка | набор, вариант, место, описание, показатель `S`, дата построения |
| новое строительство | участок, узлы, расход, ДУ, длина, способ прокладки, глубина, стоимость |
| новые тепловые камеры | камера, ДУ, число примыканий, стоимость |
| пересечения по глубине | только в расчёте с глубиной: участок, пикет, объект, проход сверху или снизу, глубины, просвет фактический и требуемый, отметка «норма выдержана» |
| свод по ДУ | суммарная длина и стоимость труб каждого условного диаметра |
| итого | новые участки, камеры, врезки в существующие камеры, стоимость строительства, штраф и всего |

Разделы реконструкции и врезок как отдельного перечня из ведомости убраны вместе
с соответствующими объектами; врезки остались строкой итога, где стоят их количество
и сумма, — это ровно то, что теперь требует раздел 6.

Свод по диаметрам — то, ради чего ведомость и открывают: объём труб одного диаметра
определяет закупку. На лучшем варианте конкурсного набора он даёт семь строк
от ДУ 65 до ДУ 300 и сходится с итогом 1 728,4 м и 197 579 372 руб.

Формат — CSV с точкой с запятой, BOM и запятой в качестве десятичного разделителя.
Всё это продиктовано Excel в русской локали: по запятой он не делит строку на столбцы,
без BOM показывает кириллицу иероглифами, а число с точкой принимает за текст
и не даёт просуммировать. Разделителей разрядов нет по той же причине.

Итоги ведомости сходятся со сводкой варианта до рубля — это закреплено тестом, потому
что ведомость, где итог не равен сумме строк, хуже, чем её отсутствие.

### 3.3.2. Независимая проверка выгрузки

Сверх требований кейса, и это главный аргумент за то, что выгрузка действительно
соответствует приложению.

`tools/validate_result.py` — отдельная реализация правил приложения на Python.
Ключевое свойство: правила в ней **записаны заново по тексту приложения**, а не взяты
из кода сервиса. Таблица 1, шкала стоимости камер, формулы стоимости и показателя,
предел угла поворота, правило четырёх примыканий, монотонность ДУ, предельная длина
по путям — всё набрано в скрипте вручную. Совпадение двух независимых реализаций —
довод; совпадение кода с самим собой — нет.

```bash
python tools/validate_result.py deliverable/result_lct2026.geojson \
    --dataset data/samples/dataset_lct2026.geojson
```

Что проверяется по каждому варианту: состав типов объектов и атрибутов; отсутствие
Z-координат; разрешимость каждой ссылки `start_node_id` / `end_node_id` против входного
набора и выгрузки; совпадение атрибута `length` с измеренной геометрией; поворот
в каждой внутренней вершине не круче 90°; допустимость `laying_method`; покрытие
расчётного расхода выбранным ДУ; стоимость каждого участка как длина на цену метра
таблицы 1, а для специального прохода — строго дороже обычного; диаметр каждой камеры
как наибольший ДУ примыкающих участков и стоимость по шкале раздела 3.2; число
примыканий не больше четырёх с учётом транзитной существующей линии; монотонность ДУ
по направлению к месту присоединения; предельная длина по каждому пути от места
присоединения; сходимость всех сумм сводки и значение `score` по формуле.

На обычной выгрузке это **1 526 проверок**, на выгрузке с глубиной — **1 607**.
Нарушений нет ни в одной.

### 3.3.3. Та же проверка внутри сервиса, для любой выгрузки

Скрипт годится нам, но он не годится департаменту: чтобы проверить подрядчика, нужна
не программа на Python в чужом репозитории, а ручка в сервисе. Она есть.

| Ручка | Что делает |
|---|---|
| `GET /api/v1/jobs/{id}/compliance` | проверяет сохранённый результат своего расчёта вместе с его входным набором |
| `POST /api/v1/compliance` | проверяет произвольную пару «выгрузка и входной набор», полученную откуда угодно |

Отчёт по каждому нарушению называет четыре вещи: код правила, формулировку требования
приложения, объекты, которыми нарушение подтверждается, и то, что именно не сошлось,
с числами. Пример: `RUN_LENGTH_LIMIT`, «раздел 2.3: предельная длина проверяется отдельно
по каждому непрерывному пути», участки `new_v1_3` и `new_v1_4`, «на пути от точки 7
подряд 1 180,0 м на ДУ 200 при пределе 1 042 м». Правил двадцать три.

Рядом с числом нарушений всегда стоит число выполненных сверок, и это не украшение:
«нарушений нет» при нуле проверок ничего не значит. На нашей выгрузке это **2 815
сверок** без нарушений. Больше, чем у скрипта, потому что проверка попарных
самопересечений перебирает все пары участков.

Отчёт честно перечисляет и то, что проверить **не удалось**. Если входной набор
не приложен, часть правил проверить нечем: диаметр камеры присоединения задаёт
разделённая ею существующая линия, а без набора её не видно. Такие правила попадают
в список `skipped`, а не молча пропускаются и не превращаются в ложные обвинения.
Этот случай нашёл тест: первая версия проверки без набора обвиняла верную выгрузку.

Правила берутся из того же подменяемого снаружи справочника, что и расчёт. Значит при
следующей смене редакции приложения проверка поедет вместе с ним, а не останется
проверять прошлогодние правила.

### 3.3.4. Разбор трассы: почему участок прошёл именно здесь

`GET /api/v1/jobs/{id}/explain` отвечает на вопрос, который задают первым: «почему труба
пошла тут, а не прямее». Для каждого участка возвращаются ограничения рядом с ним
с фактическим и требуемым расстоянием, оставшийся запас, специальные проходы и то,
насколько участок длиннее прямой между его концами.

Запас считается не вычитанием, а расстоянием до границы зоны отступа — той самой
геометрии, по которой маршрутизация проверяла проходимость. Вычитание давало бы
отрицательные значения там, где нарушения нет: контуры перед построением зоны упрощаются
с допуском в четверть метра, и расстояние до исходного контура с расстоянием
до упрощённого не совпадает. Отдельно помечается примыкание: участок, начинающийся
на существующей сети, обязан её касаться, и говорить о запасе там бессмысленно.

На конкурсном наборе разбор выходит буквальным. Участок `new_v1_2` зажат с двух сторон:
существующей сетью и домом 83, до дома остаётся сантиметр. Участок `new_v1_4` длиннее
прямой на одиннадцать процентов, потому что обходит дом 105 с запасом 1,66 м.
Участок `new_v1_1` примыкает к существующей сети в месте присоединения, и это видно
отдельной строкой, а не выглядит нарушением клиренса.

Разбор считается по готовой трассе, а не запоминается по ходу расчёта. Запоминать
пришлось бы для миллиона отвергнутых отрезков графа видимости, из которых в решение
попадут единицы; по готовой трассе тот же ответ считается за доли секунды и ровно там,
где его спросили.

### 3.3.5. Анализ чувствительности: что держит цену решения

`GET /api/v1/jobs/{id}/sensitivity` решает задачу заново без каждой точки подключения
по очереди и показывает, насколько от неё зависит стоимость и протяжённость.

Это численный эксперимент, а не вычитание длины отвода. Убрав точку, эвристика
перестраивает дерево целиком, и разница может оказаться заметно больше или меньше
ожидаемой: пропадает не только отвод, но и причина, по которой ствол шёл именно так.

На конкурсном наборе самая дорогая точка — №4: без неё решение дешевле на 27,3 млн руб.
и короче на 182,4 м, показатель падает с 12,145 до 10,833. Следом идут точки 16 и 12
с вкладом 21,3 и 20,7 млн руб. Планировщику это отвечает на вопрос, который по одному
итоговому числу не решается: какое подключение обходится дороже всего и что изменится,
если его отложить.

Стоит это дорого: один прогон около тридцати секунд, на семнадцать точек уходит порядка
девяти минут. Поэтому анализ вынесен в отдельную ручку, никогда не выполняется вместе
с обычным расчётом, и число проверяемых точек можно ограничить — самые тяжёлые
по расходу идут первыми.

## 4. Алгоритм построения маршрута с учётом глубины

Режим включается флагом `withDepth` в запросе на расчёт или переключателем «с учётом
глубины» в интерфейсе. Приложение называет его необязательным и допускает решение,
где глубина не считается вовсе: тогда геометрия остаётся двумерной, `depth_start`
и `depth_end` равны `null`, а `Kгл` принимается равным 1. Режим реализован.

### 4.1. Модель

Поверхность земли условно горизонтальна. Глубина измеряется до верхней границы
расчётного габарита новой сети. Обычная глубина 3,0 м, минимальная 0,7 м.

Два ограничения первой редакции в новой снято, и оба снятия использованы:

- **дискретного шага по глубине нет.** Прежний шаг 0,5 м был требованием старого
  текста; `Kгл` линеен по глубине, поэтому сетка не нужна и глубина подбирается
  непрерывно — ровно та, которая обеспечивает требуемый просвет, без округления
  в безопасную сторону и без переплаты за округление;
- **максимальная глубина не ограничена.** Параметр `maxDepth` остался только
  как предел поиска, а не как норма.

Габариты существующих коммуникаций и их условные глубины — из раздела 4 приложения:
газопровод 0,40 × 0,40 м на 2,8 м, силовой кабель 0,20 × 0,20 м на 2,7 м,
существующая тепловая сеть — габарит по таблице 1 и глубина 3,0 м.

### 4.2. Выбор прохождения

В месте пересечения новая сеть проходит выше или ниже коммуникации:

```
сверху: низ новой сети выше верха коммуникации на требуемый просвет
        h ≤ глубина коммуникации − просвет − высота габарита новой сети

снизу:  верх новой сети ниже низа коммуникации на требуемый просвет
        h ≥ глубина коммуникации + высота её габарита + просвет
```

Если справочник допускает оба варианта, берётся тот, у которого `Kгл` меньше, — то
есть более дешёвый. Для дорог и трамвайных путей приложение допускает только проход
под объектом и задаёт минимальную глубину верха габарита (1,0 и 1,2 м); это учитывается
как нижняя граница при проходе сверху.

**Присоединение пересечением не считается.** В месте присоединения новая сеть касается
существующей по построению; вертикальный манёвр там не нужен и невозможен. Пересечения
в пределах метра от места присоединения отсеиваются.

### 4.3. Профиль

Профиль состоит из участка изменения глубины, горизонтальной вставки в зоне пересечения
и участка возврата. Уклон не круче 0,10 м/м: на изменение глубины на метр требуется
не менее десяти метров по горизонтали. Горизонтальная вставка — 4 м, по 2 м с каждой
стороны от точки пересечения, как задают границы специального участка для подземных
коммуникаций.

Разбег берётся не с одного участка выгрузки, а с непрерывной нитки: линия делится
при смене диаметра и способа прокладки, и участок выгрузки часто короче десяти метров.
Нитка обрывается в узле ветвления — там стоит камера с одной отметкой заложения
на все примыкания, поэтому к ней трасса приходит на обычной глубине.

Новое послабление редакции 18.09 использовано: «между близкими препятствиями
допускается сохранять изменённую глубину, если все требования к пересечениям
выполняются». То есть между двумя близкими пересечениями возвращаться на 3,0 м
и снова уходить не нужно — это прямая экономия метров профиля.

Так это выглядит на конкурсном наборе. Участок `new_v1_4` глубинного расчёта разделён
техническими узлами на четыре части: подъём 9,6 м с 3,0 до 2,04 м, горизонтальная
вставка 4,0 м на 2,04 м, спуск 9,6 м обратно на 3,0 м. Уклон 0,96 м на 9,6 м — ровно
предел 0,10 м/м. Арифметика просвета проверяется на бумаге: верх габарита новой сети
на 2,04 м, высота габарита ДУ 300 по таблице 1 — 0,450 м, значит низ новой сети
на 2,49 м; верх существующей тепловой сети на 3,0 м; просвет 0,51 м при норме 0,5 м.

Если разбега не хватает и на нитке — пересечение попало на её первые метры, — профиль
не строится круче допустимого уклона. Труба проходит на обычной глубине, и в выгрузку
идёт именно она вместе с пересчитанным просветом: результат описывает построенное,
а не намерение. Такой просвет выделен в интерфейсе, а вариант с ним опускается
в ранжировании до сравнения по `S`.

### 4.4. Стоимость

```
Kгл = 1 + 0,10 · (h − 3)   при h > 3,   иначе Kгл = 1
```

На наклонном участке зависимость линейна, поэтому берётся среднее арифметическое
коэффициентов концов. Пересечение отметки 3,0 м делит участок на две части
с раздельным расчётом, и в точке деления ставится технический узел. Для стоимости
и для предельной длины берётся длина по горизонтальной проекции, а не по профилю.

В примере выше `Kгл` равен единице на всех четырёх частях: манёвр идёт вверх,
а выше трёх метров надбавки нет. Это не изъян расчёта, а его результат — проход
поверх коммуникации выбран именно потому, что не стоит ничего, тогда как проход снизу
потребовал бы уйти ниже 3,0 м и заплатить за каждый метр.

### 4.5. Что попадает в результат и как ранжируется

В выгрузке: `depth_start` и `depth_end` каждого участка, технические узлы в точках
деления профиля, пересчитанная стоимость участков и сводка варианта. Z-координат нет —
приложение их не требует, вертикаль задают атрибуты. Разбор пересечений — с указанием
прохода сверху или снизу, фактического и требуемого просвета — остаётся в API
и в ведомости объёмов работ.

Ранжирование выполняется **внутри режима и отдельно от двумерного**: набор вариантов
свой, файл свой, места свои. Перед сравнением по `S` идёт число невыдержанных
вертикальных просветов: неисполнимость — не вопрос стоимости.

На конкурсном наборе режимы дают разных лидеров, и это содержательный результат,
а не шум:

| | Двумерный режим | Режим с глубиной |
|---|---|---|
| Место 1 | v1, одна сеть, S = 12,145 | v3, две части, S = 12,244 |
| Лучшая сеть | 1 728,4 м, 248 579 372 руб. | 1 710,2 м, 254 064 260 руб. |
| Время расчёта | около 35 с | около 23 с |

Лидер глубинного режима идёт на обычной глубине 3,0 м целиком: его трасса пересечений
не даёт. Отклонения по глубине — от 2,04 до 3,0 м — появляются у варианта, занявшего
в этом режиме второе место (S = 12,335, сеть 1 732,5 м, 254 928 019 руб., 34 участка
и 4 технических узла). То есть манёвр по глубине стоит денег, и вариант, которому
манёвр не нужен, по этой причине выигрывает — а объединять два ранжирования нельзя,
иначе этот эффект пропал бы.

## 4б. Проверка предела по объёму входных данных

Раздел 3.2 ТЗ задаёт входной файл до 3 ГБ. Это проверено загрузкой, а не настройкой:
`tools/make_large_dataset.py` собирает набор заданного размера из конкурсного,
размножая пространственные ограничения со смещением и уникальными идентификаторами.

| Размер файла | Объектов | Время разбора | Пик памяти контейнера |
|---|---|---|---|
| 0,2 ГБ | 84 606 | 4,7 с | 2,2 ГБ |
| 1,0 ГБ | 421 298 | 26,5 с | 2,9 ГБ |
| 3,0 ГБ | 1 262 935 | 98,2 с | 6,0 ГБ |

Измерение выполнено на контейнере с 7,6 ГБ памяти и кучей 5,7 ГБ — меньшей, чем
у машины из требований. Проверка нашла три дефекта, которые иначе проявились бы
только на защите:

1. Файл размером ровно 3 ГБ отвергался с кодом 413: multipart добавляет к файлу
   заголовки части, и при пределе ровно 3 ГБ запрос в него не помещается. Пределы
   Spring и nginx подняты до 4 ГБ.
2. Разбор держал одновременно сырые объекты с картами атрибутов и построенную модель
   и заканчивался `OutOfMemoryError`. Ссылка на сырой объект снимается сразу после
   преобразования.
3. Протокол допущений хранил полный перечень идентификаторов по каждому замечанию.
   Теперь — не более пятидесяти на запись, с полным счётом в тексте.

Разбор входа редакция приложения не затронула, поэтому замер не повторялся.

## 5. Границы применения решения

### 5.1. Что не выполняется по условиям кейса

- Полный гидравлический расчёт: давление, потери напора, скорость теплоносителя,
  насосные режимы и балансировка сети. Вместо него — предельная длина непрерывного
  пути одного условного диаметра, как и предусматривает раздел 2.3 приложения.
- **Реконструкция существующей сети и существующих камер** — исключена самим
  приложением (п. 2.4, разъяснение №14), а не нами. Текущий расход и резерв
  пропускной способности существующей сети в обязательном расчёте не определяются.
- Расчёт и развитие мощности источника.
- Реальный рельеф, фактические высотные отметки коммуникаций, геология
  и грунтовые воды.
- Взаимные пересечения существующих коммуникаций между собой.
- Надземная прокладка; базовый способ — подземная бесканальная.
- Положение ИТП внутри здания.
- Рабочее проектирование, расчёты прочности, компенсаторы, конструкция камер
  и специальных переходов.

### 5.2. Принятые допущения там, где входные данные молчат

Каждое допущение записывается в протокол разбора с кодом и списком затронутых
объектов и видно в интерфейсе и через API.

| Чего нет во входных данных | Что принято | Код записи |
|---|---|---|
| `diameter` у тепловой камеры | наибольший ДУ примыкающих участков — то же правило, по которому раздел 3.2 определяет ДУ новой камеры | `chamber.diameterInferred` |
| число примыканий к существующей камере | восстанавливается по геометрии: транзитная линия, разделённая камерой, занимает два места из четырёх | `chamber.transitDegree` |
| точка подключения у полигона ОКС | ближайшая к сети точка контура объекта | `oks.connectionPointDerived` |
| тип ограничения вне таблицы 2 | разрешается через словарь псевдонимов; неизвестный обходится с зазором 1 м и попадает в диагностику | `restriction.summary` |
| `flow_tph` у существующей сети | расход принят нулевым; в обязательном расчёте не используется вовсе | `segment.noFlow` |

Отдельно: в конкурсном наборе все семнадцать точек подключения лежат **внутри**
полигонов ограничений типа `oks`, на 0,06–8,3 м от границы. Эти полигоны опознаны
как контуры самих подключаемых объектов, и раздел 2.2 приложения ровно такой случай
и описывает: один финальный прямой участок от ближайшей границы полигона до точки,
без требования отступа к своему полигону. Без такого опознания собственный полигон
закрывает подход к своей же точке буфером в пять метров, и маршрут не находится
никогда. Запись протокола — `oks.footprintFromRestriction`.

Два допущения первой редакции исчезли вместе с требованиями:

- **цепочка `upstream_object_id` к источнику** больше не нужна расчёту. Она
  восстанавливается обходом графа от источника и остаётся в диагностике — как
  проверка связности существующей сети, а не как вход в расчёт.
- **расход существующей сети** перестал влиять на результат. В первой редакции он
  определял объём реконструкции, и предположение о загрузке сети было самым
  влиятельным во всём решении; таблицу чувствительности к нему приходилось приводить
  здесь отдельно. Теперь резерв существующей сети в обязательном расчёте
  не определяется, переключателя «сеть загружена» в API нет, и таблица снята: она
  описывала бы величину, которой в расчёте больше нет. Режим `CAPACITY_FRACTION`
  сохранён как исследовательская настройка сервиса (`heatroute.ingest.existingFlowMode`)
  и в обязательном расчёте не участвует.

Скорректированный датасет от 18.09 убрал ещё одно допущение: источник теперь
координатно совпадает с началом участка 116, и привязка источника к сети больше
не восстанавливается — запись `source.snapped` на этом наборе не появляется.

### 5.3. Пределы метода

**Эвристика не гарантирует глобального оптимума.** Дерево Штейнера NP-трудно;
применяемая эвристика кратчайшего пути даёт результат не хуже удвоенного оптимума,
а восемь запусков с разными затравками сокращают разрыв на практике. Результат
воспроизводим: повторный расчёт на тех же данных даёт те же числа.

**Клиренс графа берётся по наибольшему диаметру варианта.** Это гарантирует соблюдение
нормы, но на плотной застройке может закрыть проход, которого хватило бы для тонкой
ветви: отводы проверяются по своему диаметру только там, где отрезка нет в графе
(раздел 1.10). Обходной путь есть и не требует пересборки — расчётный диаметр
клиренсов задаётся полем `designDiameter` запроса или параметром
`heatroute.routing.initial-design-dn`. На конкурсном наборе он равен 400 мм при
фактическом наибольшем ДУ новой сети 300 мм, то есть запас — одна ступень.

Соблазнительная мысль — строить для дробных разбиений отдельный граф под меньший
диаметр — проверена на первой редакции модели и отвергнута: зависимость показателя
от расчётного диаметра оказалась не монотонной, потому что другой граф уводит
эвристику в другой локальный оптимум, иногда лучше, иногда хуже. Второй граф стоил бы
секунд расчёта и заметного усложнения кода ради выигрыша, который не гарантирован.
Правильное решение — граф, где у каждого ребра известен предельный диаметр,
и магистраль ищется по одним рёбрам, а тонкие отводы по другим; оно не сделано,
потому что перестройка графа перед сдачей опаснее известного и ограниченного предела.

**Обратная связь от профиля к маршрутизации работает перебором, а не оптимизацией.**
Если манёвр по глубине не помещается, сервис ставит вокруг пересечения зону запрета
радиусом в недостающий разбег и строит вариант заново — тем же механизмом, которым
независимые части сети обходят друг друга. Нарушение при этом снимается не всегда;
тогда трасса остаётся исходной, нарушение показывается, вариант понижается. Глубина
как переменная в самом поиске маршрута не участвует.

**Приведение угла поворота не всегда возможно.** Дуга снаружи вершины ограничена
по радиусу снизу: мельче полуметра звенья сами становятся запрещённой мелкой ломаной.
Если рядом второе препятствие и дугу не вписать, вершина остаётся круче 90°
и попадает в счётчик нарушений. На конкурсном наборе таких вершин нет ни в одном
варианте, но гарантии в общем случае нет, и она не заявляется.

**Порог «прохода рядом» — эвристика.** Приложение требует соблюдать минимальное
расстояние при проходе рядом и не проверять его внутри разрешённого пересечения,
но численной границы между этими случаями не даёт. Сервис различает их по длине хода
внутри зоны отступа с порогом 3 м (раздел 1.10.1). Порог вынесен в настройку именно
потому, что это наше решение, а не норма.

**Плотность обстановки.** Граф видимости строится по вершинам буферизованных
контуров, и его размер растёт квадратично от их числа. На конкурсном наборе это
3 545 узлов и 96 027 рёбер. Если проверочный набор окажется на порядок плотнее,
граф заменяется навигационной сеткой по ограниченной триангуляции Делоне —
построение дерева работает с узлами и рёбрами и не знает, откуда они взялись.

### 5.4. Универсальность

Координаты, идентификаторы и конфигурация конкурсного набора нигде не зафиксированы
в коде — требование раздела 2.14 ТЗ и разъяснения №17: «координаты, количество
объектов и геометрию переданного конкурсного файла зашивать в алгоритм нельзя».
Проверять будут на других данных, выгруженных из рабочих систем.

Справочник приложения — таблица 1, шкала стоимости камер раздела 3.2, таблица 2
правил по типам ограничений, условные габариты и глубины коммуникаций, параметры
разделов 5 и 6 — целиком вынесен в файл
`backend/src/main/resources/reference/heatroute-reference.yml` и подменяется снаружи
без пересборки:

```bash
java -jar heatroute.jar --spring.config.additional-location=file:/opt/heatroute/
```

Текущие значения справочника доступны через `GET /api/v1/reference` — по нему
значения сверяются с приложением построчно.

Зона проекции задана параметром `heatroute.geo.utm-zone`, а не константой: набор
из другого региона обрабатывается сменой параметра. Расчёты длин, расстояний
и габаритов идут в EPSG:32637, как требует раздел 1.

Обе ветки разбора — когда атрибуты во входных данных есть и когда их нет —
реализованы и покрыты тестами. Для проверки изготовлен набор с полным составом
атрибутов: скрипт `tools/make_full_dataset.py` достраивает конкурсный набор
до состава раздела 1.1, а тест `FullSpecDatasetTest` доказывает, что на нём
не восстанавливается ничего — всё берётся из входных данных, и расчёт проходит
тем же кодом.

Поддержка типов ограничений сверх таблицы 2 — метро, школы, детские сады,
больницы — сделана словарём псевдонимов. Разъяснение №9 говорит, что это
не обязательно, но «может учитываться как преимущество при экспертном сравнении
решений с сопоставимым качеством выполнения обязательной части». Обратная правка
тоже сделана: псевдоним `railway → tram_tracks` убран, потому что с 18.09
у железной дороги своя строка таблицы 2 с запретом пересечения, и псевдоним
подменял бы норму более мягкой.

со специальным объектом, которая с первого раза сделала недостижимыми все семнадцать
точек. Ни одну из этих ошибок нельзя было увидеть чтением кода.
